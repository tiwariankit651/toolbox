Working With Unix Time: Units, Time Zones and the Edge Cases That Trip People Up

What the epoch is, and why the unit matters

A Unix timestamp is a single number: the count of seconds since 1 January 1970 00:00:00 UTC, a fixed point called the epoch. Because it is anchored to UTC, the same number means the same instant everywhere on Earth — the ambiguity only appears when you display it. The catch is the unit. Plain Unix time is in seconds (ten digits for current dates), but JavaScript, Java and many databases store milliseconds (thirteen digits), and high-resolution systems use microseconds or nanoseconds. This tool guesses the unit from the digit count — up to 11 digits is seconds, up to 14 milliseconds, up to 17 microseconds, longer is nanoseconds — so 1700000000 and 1700000000000 both resolve to the same moment, Tuesday 14 November 2023 22:13:20 UTC. If your value is unusual you can force the unit with the dropdown rather than relying on the guess.

Negative timestamps and the range limit

Dates before 1970 are represented by negative numbers, and they work here: -86400 is exactly one day before the epoch, 1969-12-31T00:00:00Z. The sign is stripped before counting digits so the unit detection still behaves. There is an outer limit — JavaScript can only represent dates within about 273,790 years either side of 1970 — and a value beyond that is rejected with a message rather than producing a nonsense date.

Converting a date back to a timestamp in a specific zone

Going from a human date to an epoch is where most mistakes happen, because a wall-clock time is meaningless without a zone. "1 January 2026, midnight" is a different instant in Mumbai than in London. The Date to Timestamp section asks you which zone the time is written in and computes that zone's real offset for that date, so 2026-01-01 00:00 in Asia/Kolkata gives 1767205800. The offset is derived from the browser's own time zone database by formatting the instant in the target zone and reading it back, which is exact for daylight saving and for half-hour zones like India's +5:30.

Daylight-saving gaps, ambiguous times and 2038

Two dates a year behave strangely. On the spring-forward date a range of wall-clock times never happens because the clock jumps — 2024-03-10 02:30 in America/New_York is one such non-existent time — and the tool shows a note and uses the instant just after the skip. On the fall-back date a time happens twice; 2024-11-03 01:30 in New York is ambiguous, and the tool uses the earlier occurrence and says so. Finally, the Year 2038 problem: 2147483647 seconds is 2038-01-19T03:14:07Z, the largest value a signed 32-bit integer holds. One second later it overflows, which still threatens legacy and embedded systems. The tool flags this value when you enter it. Everything is computed locally; nothing is uploaded.

Frequently Asked Questions

How does the tool know if my number is seconds, milliseconds, microseconds or nanoseconds?

It counts the digits. A value with up to 11 digits is read as seconds, up to 14 as milliseconds, up to 17 as microseconds, and longer as nanoseconds — so 1700000000 is seconds and 1700000000000 is milliseconds. The sign is ignored for counting, so negative (pre-1970) values are detected the same way. You can override the guess with the unit dropdown if your value is unusual.

Why does the Date to Timestamp result use the time zone I pick instead of my computer's?

Because the same wall-clock time means a different instant in each zone. The tool reads your date and time as if they were written on a clock in the zone you choose, works out that zone's exact offset for that specific date (including daylight saving) using the browser's time zone data, and then produces the epoch. That is why 2026-01-01 00:00 in Asia/Kolkata gives 1767205800, not whatever your own zone would give.

What happens with a daylight-saving gap or an ambiguous time?

On the spring-forward date some wall-clock times do not exist (the clock jumps, e.g. 02:30 in America/New_York), and on the fall-back date some times happen twice. The tool detects both by comparing the offset before and after the moment: for a gap it uses the instant just after the skip and shows a note, and for an ambiguous time it uses the earlier of the two occurrences and says so, rather than silently picking one.

What is the year 2038 problem the tool mentions?

Unix time stored in a signed 32-bit integer can only reach 2147483647, which is 2038-01-19T03:14:07Z. One second later the value overflows to a negative number, so systems using 32-bit time break. When you enter 2147483647 as seconds the tool shows this date and flags it. Modern 64-bit systems are not affected, but legacy code and some embedded devices still are.
