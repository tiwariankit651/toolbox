🔑 JWT Decoder

Decoding is not verification. Reading a token only shows what it claims; it does not prove the claims are genuine. Everything here runs in your browser — the token is never sent anywhere. Do not paste a real production token into any online tool you do not trust.

Verify signature (optional)

Verification happens locally with the Web Crypto API. For HS256/384/512 provide the shared secret; for RS256/384/512 and ES256/384 provide the public key (PEM SPKI or JWK). The token and key stay in your browser.

How to Use This Tool

  1. Paste the token into the box. It decodes as you type — no button needed, though Decode re-runs it.
  2. Read the colour-coded token: the header is red, the payload purple and the signature green, matching the three dot-separated parts.
  3. Review the claims: the header and payload are shown as formatted JSON, and standard claims (iss, sub, aud, exp, nbf, iat, jti) are explained, with the time claims shown as dates and an expiry status.
  4. Verify if you need to: open the verify section, choose HMAC or RSA/ECDSA, paste the secret or public key, and click Verify. You will see "Verified" or "Invalid signature".
  5. Stay safe: decoding never checks authenticity, and the alg: none case is flagged as unsafe.

Common Use Cases

  • Debugging auth — see exactly what claims your backend put in a token when a request is unexpectedly rejected.
  • Checking expiry — read the exp claim as a real date and see whether a token is still valid or how long ago it expired.
  • Inspecting a third-party token — decode an OAuth/OIDC ID token to confirm issuer, audience and subject.
  • Confirming a signature — verify an HS256 token against a secret, or an RS256/ES256 token against a public key, without any server round-trip.
  • Spotting the none algorithm — catch unsigned tokens, a classic JWT security pitfall.

About This Tool

A JWT has three Base64URL parts separated by dots: a header, a payload, and a signature. This tool decodes the first two (with a UTF-8 decoder, so non-ASCII claims such as Hindi names display correctly) and can optionally verify the signature using the browser's built-in Web Crypto API. A five-part token is JWE — encrypted — and cannot be decoded here without the decryption key.

Nothing is uploaded. The token, any secret and any key you paste stay in your browser and are never transmitted. This is why it is safe to use, but also why decoding alone tells you only what the token claims, not whether those claims are trustworthy.

Reading and Verifying JSON Web Tokens Safely in the Browser

The three parts, and why two of them are readable

A JWT is three Base64URL strings joined by dots: a header, a payload and a signature. The tool colours them to match — header in red, payload in purple, signature in green — so you can see the structure at a glance. The header and payload are only encoded, not encrypted, which is why anyone can decode them and why this tool can show them to you. Decoding fixes the Base64URL padding, swaps the URL-safe characters back, and runs the bytes through a UTF-8 decoder, so a claim such as "नाम":"अंकित" displays its real characters instead of mojibake. The header and payload are then pretty-printed as JSON. If the input has five parts it is a JWE — an encrypted token — and the tool says it cannot be read without the decryption key rather than printing nonsense.

Standard claims and expiry

The payload often carries registered claims, and the tool explains each one it finds: iss (issuer), sub (subject), aud (audience), exp (expiry), nbf (not before), iat (issued at) and jti (unique id). The three time claims are numeric epochs, so they are rendered as real dates. For exp the tool compares against the current time and shows either "Valid, expires in…" or "Expired … ago"; for nbf it warns if the token is not yet valid. This is the quickest way to answer the common question "is this token still good?" without pasting it into a backend.

Decoding is not verification

This is the point worth repeating. Because the payload is plain Base64URL, anyone can edit it and re-encode it. A decoded payload tells you what the token claims, not whether a trusted server actually issued it. The only thing that proves authenticity is the signature, computed by the issuer over the header and payload with a key you do not have unless you are the issuer or hold its public key. The tool also flags the dangerous alg: none case, where a token is unsigned — any system that accepts such a token is trusting its contents blindly, a classic JWT exploit.

Verifying signatures with Web Crypto

The optional verify section uses the browser's Web Crypto API, so the token and key never leave your device. For HS256/384/512 you paste the shared secret (text, or base64 if you tick the box) and the tool checks the HMAC. For RS256/384/512 and ES256/384 you paste the public key as a PEM SPKI block or as JWK JSON, and the tool imports it and verifies. It recomputes the signature over header.payload, so altering a single character of the payload turns a "Verified" into "Invalid signature". One subtlety for elliptic-curve tokens: a JWS ES signature is the raw r‖s concatenation, which is exactly what Web Crypto expects — no DER conversion is needed here, unlike when checking against tools such as OpenSSL that emit DER. Malformed input, a bad key format or a mismatched algorithm produce a clear message rather than a crash.

Frequently Asked Questions

Does decoding a JWT prove it is genuine?

No. The header and payload are only Base64URL-encoded, not encrypted, so anyone can read and even forge them. Decoding shows what a token claims; it says nothing about whether those claims were really issued by the server. To prove authenticity you must verify the signature with the correct secret or public key, which is what the optional verify section does. Treat a decoded payload as untrusted until it is verified.

Which algorithms can this tool verify, and how?

Verification runs in your browser with the Web Crypto API. For HS256, HS384 and HS512 you supply the shared secret (plain text, or tick the box if it is base64). For RS256/384/512 and ES256/384 you supply the public key as PEM (an SPKI 'BEGIN PUBLIC KEY' block) or as JWK JSON. The tool recomputes the signature over header.payload and reports Verified or Invalid signature. Changing even one character of the payload makes a valid signature fail.

Why does a token with five parts say it cannot be decoded?

A five-part token is a JWE (JSON Web Encryption), not a JWS. Its payload is encrypted, so unlike a normal signed JWT it cannot be read by decoding alone — only someone with the decryption key can see the contents. The tool detects the five-part structure and tells you this rather than printing garbage. A normal readable JWT has exactly three parts.

Why do non-ASCII claims like Hindi names display correctly here?

The Base64URL payload is decoded to raw bytes and then run through a UTF-8 TextDecoder, so multi-byte characters are reconstructed properly. A naive atob() alone would mangle them. That means a claim such as "नाम":"अंकित" shows its real characters. The tool also fixes Base64URL padding and translates the URL-safe characters before decoding, and reports a clear message instead of crashing on malformed input.
