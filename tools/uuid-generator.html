🆔 UUID Generator

🔎 Validate & Inspect a UUID

Paste any UUID to check whether it is well-formed and see its version, variant, and — for v7 — the millisecond timestamp embedded in it decoded to a date.

Frequently Asked Questions

What is the difference between the v4 and v7 UUIDs it generates?

v4 is 122 bits of cryptographic randomness with the version nibble fixed to 4 and the variant bits to 10 — ideal when you only need uniqueness and no ordering. v7 (RFC 9562) starts with a 48-bit Unix millisecond timestamp, then the version 7 and variant 10 bits, then random data, so a lexicographic sort of v7 UUIDs matches creation order. That ordering makes v7 far friendlier as a database primary key because new rows cluster at the end of the index instead of scattering like v4.

Where does the randomness come from — is it secure?

v4 uses the browser's native crypto.randomUUID() when present, and otherwise falls back to crypto.getRandomValues() with the version and variant bits set correctly by hand. v7 always fills its random portion from crypto.getRandomValues(). Both draw on the browser's cryptographically secure random generator, not Math.random(), and everything happens locally in the page.

If I generate a bulk batch, do the v7 UUIDs stay in order?

Yes. Many v7 UUIDs in a batch are created within the same millisecond, which would otherwise leave their order to chance. This tool keeps a per-millisecond counter in the 12 'rand_a' bits, so UUIDs minted in the same millisecond increment that counter and therefore sort in the exact order they were generated. You can generate from 1 to 1000 at once.

What does the validator tell me, and does it decode v7 timestamps?

Paste any UUID — in standard, uppercase, hyphen-free, brace or urn:uuid form — and it reports whether the string is well-formed (32 hex digits in the 8-4-4-4-12 layout), its version nibble and its variant bits. It specially recognises the nil UUID (all zeros) and the max UUID (all ones). For a v7 UUID it reads the 48-bit timestamp back out and shows it both as milliseconds since the epoch and as a decoded UTC and local date.

Generating v4 and v7 UUIDs, and Reading One Back

v4: random, with a safe fallback

A version 4 UUID is almost entirely random — 122 bits of it — with only the version nibble pinned to 4 and two variant bits pinned to 10. This tool generates one by calling the browser's native crypto.randomUUID() when it exists, because that is the fastest and most direct route. On an older engine that lacks it, the tool falls back to pulling sixteen bytes from crypto.getRandomValues() and setting those same version and variant bits by hand, so the output is indistinguishable and still backed by a cryptographically secure source. The practical upshot: v4 is the right choice whenever you need uniqueness and nothing more. It carries no timestamp, so you cannot sort v4 UUIDs into any meaningful order, and as database keys they scatter across an index.

v7: time first, so the IDs sort by creation order

Version 7, defined in RFC 9562, fixes the sorting problem. The first 48 bits are the current time as Unix milliseconds, laid out big-endian, followed by the version 7 nibble, the variant 10 bits, and random data for the rest. Because the timestamp leads, a plain text sort of v7 UUIDs is a chronological sort — which is why v7 makes a far better primary key than v4: new rows append to the end of the index instead of landing anywhere.

There is a subtlety the tool handles for you. When you ask for a bulk batch, many UUIDs are created inside the same millisecond, and if the trailing bits were pure random their order would be arbitrary. To keep sorted order equal to generation order, the tool keeps a counter that resets each millisecond and packs it into the 12 "rand_a" bits after the timestamp. Generate a thousand v7 UUIDs at once and they still sort exactly as they were made.

The validator: version, variant and the v7 timestamp

Paste any UUID into the inspector and it first normalises the input — it tolerates braces, a urn:uuid: prefix, uppercase and even hyphen-free 32-character strings — then checks it against the 8-4-4-4-12 hex pattern. A malformed string is rejected with a clear message. A valid one has its version nibble and variant bits decoded and named, and the two special values are called out explicitly: the nil UUID of all zeros and the max UUID of all ones. For a v7 UUID the inspector reads the 48-bit timestamp back out of the first twelve hex digits and shows it as milliseconds since the epoch alongside a decoded UTC and local date, so you can tell exactly when an ID was minted.
