What this formatter preserves, drops, and how it converts between formats

How XML is parsed and re-serialised safely

The XML side never uses a regex to guess at structure. It hands your text to the browser's built-in DOMParser in application/xml mode, which builds a real document tree. That parser does not execute scripts, and the tool makes a second guarantee on top of it: the formatted result is only ever written into a read-only text box through the element's value, never injected into the live page. So even markup that looks like a script or an HTML tag is treated as inert text. If the document is not well-formed, the parser produces a parsererror node; the tool reads its message and, where the browser supplies them, the line and column, and shows them in the status line. The Validate button runs exactly this check and reports whether the document is well-formed without producing any output.

Indentation and the whitespace rules

Formatting walks the parsed tree and rebuilds the text with your chosen indent — two spaces, four spaces, or a tab. The declaration line (<?xml …?>) is recovered from the source because the parser drops it, and comments, CDATA sections and processing instructions are written back at their proper depth. Whitespace is where most formatters get XML wrong, so the rules here are deliberate: whitespace-only text nodes between elements are treated as layout and collapsed, but any element carrying xml:space="preserve" has its entire contents serialised untouched, spaces and all. An element whose only child is text stays on one line; an element with child elements is broken out and indented. Minify applies the same preserve rule while stripping the inter-element whitespace, so a formatted document and its minified form carry the same data and round-trip back to each other.

YAML, and why comments disappear

YAML is handled by js-yaml 4.1.0. Loading parses one or more documents — streams separated by --- are supported — and dumping writes them back with your indent and an optional alphabetical key sort. Two honest limitations follow from how js-yaml works. First, it resolves anchors and aliases into plain values, so a &anchor/*alias pair becomes duplicated data rather than a reference. Second, comments are not part of the parsed model at all, so re-dumping loses every # comment; the tool detects comments in your input and warns you in the status line rather than pretending they survived. A malformed document throws an error whose line and column are shown. Non-Latin text — Hindi, for instance — passes through unchanged.

Converting to and from JSON

Both formats convert to JSON and back. YAML↔JSON is a direct load-and-stringify in each direction. XML→JSON maps each element to an object key, stores attributes under @-prefixed keys, groups repeated sibling elements into an array, and keeps mixed text under a #text key; JSON→XML reverses that convention and prepends a declaration. Order-sensitive or heavily mixed-content XML will not always return byte-for-byte, but ordinary configuration and data documents convert cleanly both ways, which is usually all you need to inspect a structure or feed it to another tool.
