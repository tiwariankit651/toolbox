Hashing Text and Large Files Correctly in the Browser

Why text is hashed as UTF-8, and the trailing-newline trap

A hash is computed over bytes, not characters, so the first question any hashing tool has to answer is how it turns your text into bytes. This tool encodes text as UTF-8 with the browser's TextEncoder before hashing. That matters the moment you type anything outside plain ASCII: the string "नमस्ते" is six Unicode code points but eighteen UTF-8 bytes, and its SHA-256 only matches Python's hashlib.sha256("नमस्ते".encode()).hexdigest() because both sides agree on UTF-8. If a tool silently hashed UTF-16 or Latin-1 instead, your result would disagree with every command-line tool and you would waste an afternoon finding out why.

The second trap is the invisible newline. Text editors and shells habitually append a line feed to the end of a file, so echo abc | sha256sum hashes four bytes, not three, and disagrees with the digest of the literal string "abc". The Trim one trailing newline checkbox removes a single \n or \r\n from the end of your input so you can reproduce a checksum taken either way. Everything you type is hashed live, so the digests update on each keystroke.

How a gigabyte file is hashed without freezing the tab

The Web Crypto API (crypto.subtle.digest) is excellent but has two limits that shape this tool: it has no MD5, and it has no streaming — you hand it one buffer and wait. Loading a 1 GB file as a single buffer to hash it is exactly how a browser tab locks up or runs out of memory. So for the two algorithms whose incremental implementations are verified here, MD5 (via SparkMD5) and SHA-256 (a pure-JavaScript FIPS 180-4 implementation), the file is read in 4 MB slices and fed to the hashing state one slice at a time. Memory stays flat, a progress bar advances, and the event loop yields between slices so the page stays responsive.

SHA-1, SHA-384, SHA-512 and file HMAC are computed with Web Crypto over the whole file, which means they are offered only up to 512 MB. Above that the tool says so plainly rather than pretending; MD5 and SHA-256 still work at any size. This is an honest trade-off: streaming code is shipped only where it has been checked against known answers.

HMAC, output formats, and comparing a hash

Leave the key box empty for plain hashes. Type a secret and the SHA-256/384/512 rows become HMAC, keyed via Web Crypto, which is what you need to sign or verify an API request. Output can be lowercase hex, uppercase hex, or Base64 — different systems publish checksums in different forms, and the Compare box accepts any of them. Paste the hash you expect and it is matched, case-insensitively, against every value on the page, so verifying a download is a glance at a green or red banner.

When not to trust MD5 or SHA-1

Both are marked "not for security" for a reason: practical collision attacks exist, so an attacker can craft two different files with the same MD5 or SHA-1. They remain fine for catching accidental corruption or as cache keys, but for integrity you can rely on, or anything an adversary might attack, use SHA-256 or stronger.
