Reading and Verifying JSON Web Tokens Safely in the Browser

The three parts, and why two of them are readable

A JWT is three Base64URL strings joined by dots: a header, a payload and a signature. The tool colours them to match — header in red, payload in purple, signature in green — so you can see the structure at a glance. The header and payload are only encoded, not encrypted, which is why anyone can decode them and why this tool can show them to you. Decoding fixes the Base64URL padding, swaps the URL-safe characters back, and runs the bytes through a UTF-8 decoder, so a claim such as "नाम":"अंकित" displays its real characters instead of mojibake. The header and payload are then pretty-printed as JSON. If the input has five parts it is a JWE — an encrypted token — and the tool says it cannot be read without the decryption key rather than printing nonsense.

Standard claims and expiry

The payload often carries registered claims, and the tool explains each one it finds: iss (issuer), sub (subject), aud (audience), exp (expiry), nbf (not before), iat (issued at) and jti (unique id). The three time claims are numeric epochs, so they are rendered as real dates. For exp the tool compares against the current time and shows either "Valid, expires in…" or "Expired … ago"; for nbf it warns if the token is not yet valid. This is the quickest way to answer the common question "is this token still good?" without pasting it into a backend.

Decoding is not verification

This is the point worth repeating. Because the payload is plain Base64URL, anyone can edit it and re-encode it. A decoded payload tells you what the token claims, not whether a trusted server actually issued it. The only thing that proves authenticity is the signature, computed by the issuer over the header and payload with a key you do not have unless you are the issuer or hold its public key. The tool also flags the dangerous alg: none case, where a token is unsigned — any system that accepts such a token is trusting its contents blindly, a classic JWT exploit.

Verifying signatures with Web Crypto

The optional verify section uses the browser's Web Crypto API, so the token and key never leave your device. For HS256/384/512 you paste the shared secret (text, or base64 if you tick the box) and the tool checks the HMAC. For RS256/384/512 and ES256/384 you paste the public key as a PEM SPKI block or as JWK JSON, and the tool imports it and verifies. It recomputes the signature over header.payload, so altering a single character of the payload turns a "Verified" into "Invalid signature". One subtlety for elliptic-curve tokens: a JWS ES signature is the raw r‖s concatenation, which is exactly what Web Crypto expects — no DER conversion is needed here, unlike when checking against tools such as OpenSSL that emit DER. Malformed input, a bad key format or a mismatched algorithm produce a clear message rather than a crash.
