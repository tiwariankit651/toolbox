🔍 Regex Tester Guide

October 2026 · 9 min read

A regular expression that compiles without error and still does the wrong thing is the hardest kind of bug to find, because there is nothing to read. The pattern looks right, the test string looks right, and the match count is simply not what you expected. Almost always the cause is one of a small number of behaviours that are easy to forget and impossible to infer from the result.

This guide covers those behaviours, with the specific symptom each one produces, so you can recognise the failure rather than rebuild the pattern from scratch.

The dot does not cross a line break

By default . matches any character except a newline. So this pattern:

a.b  against  a\nb  →  no match

which is surprising, because "any character" sounds like it should include a newline. Adding the s flag — dotAll — changes that and the same pattern matches. The symptom to watch for is a pattern that works on a single line and finds nothing in a multi-line block.

This matters most when extracting from HTML or log files, where the thing you want routinely spans lines. If a pattern suddenly stops matching when you paste in real data rather than a one-line sample, the s flag is the first thing to check.

Anchors match the whole string, not each line

^ and $ mean start and end of the subject, not of a line. Against a three-line block, ^error will only match if the very first line begins with "error". The second and third lines are invisible to it.

The m flag — multiline — redefines both anchors to mean start and end of a line. This is the flag most often missing when someone is filtering log lines and getting one result instead of several.

A related trap: $ matches before a trailing newline as well as at the very end, so a pattern ending in $ can match a line that still has its line break attached. If you are capturing with $ and getting a stray newline in the result, that is why.

Without the g flag you get one match, and replace changes one thing

This is the single most common surprise. "a1b2c3".replace(/\d/, "x") gives "axb2c3" — only the first digit. With /\d/g it gives "axbxcx".

It also affects counting. Without g, match() returns a rich object describing one match with its capture groups. With g, it returns a plain array of every matched string and no capture groups at all. If your capture groups suddenly become undefined after you add the g flag, that is the reason, and matchAll() is the fix.

Nested quantifiers can hang the browser

A pattern like (a+)+b looks harmless. Against "aaaaaaaaaaaaaaaaaaaaaaaaaaaa" with no b at the end, the engine tries every way of dividing those characters between the inner and outer repetition before concluding there is no match. The number of combinations grows exponentially with the input length.

This is catastrophic backtracking, and it is a real denial-of-service vector when a pattern is applied to user input on a server. The shape to recognise is a quantifier applied to a group that itself contains a quantifier: (x+)*, (x*)+, (a|aa)+. If a pattern of that shape is unavoidable, make the inner part unambiguous so there is only one way to match.

Inside square brackets, most characters stop being special

A character class is a different language. [.] matches a literal dot — no escaping needed, and [\.] works but is redundant. The characters that remain special inside a class are ^ (only as the first character, where it negates), - (between two characters, where it makes a range), ] and \.

Which means [a-z-] is valid, with the trailing hyphen literal, and [1-3-5] is probably not what you intended. A hyphen you want taken literally is safest at the start or the end of the class.

\d and \w are ASCII-only, even with the u flag

This one matters a great deal for Indian-language text. \d matches 0-9 and nothing else — not Devanagari digits. \w matches [A-Za-z0-9_] only, so a name written in Hindi matches none of it.

Adding the u flag does not change this. What u gives you is correct handling of characters outside the basic plane, plus access to Unicode property escapes: \p{L} for any letter in any script, \p{Nd} for any decimal digit, \p{Script=Devanagari} for that script specifically. If you are validating names or addresses for an Indian audience, \w will silently reject legitimate input and \p{L} will not.

The same gap catches filename sanitising. A routine that strips everything matching [^\w] will remove every Devanagari character, leaving an empty name.

Greedy by default, and what that costs

<.+> against <a>text</a> matches the entire string, not just <a>, because + takes as much as it can and then gives back only what it must. Adding ? makes it lazy: <.+?> matches <a> alone.

Lazy quantifiers are not automatically better. They are slower on long non-matching input, because the engine extends one character at a time. For a bounded case a negated class is usually the best of the three: <[^>]+> expresses "up to the next closing bracket" directly, with no backtracking at all.

Capture groups, and when not to capture

Every ( ) creates a numbered group and stores what it matched. If you only need the grouping for a quantifier or an alternation, (?: ) does the same job without the storage, which keeps your group numbers stable when you edit the pattern.

Named groups — (?<year>\d{4}) — are worth the extra characters as soon as a pattern has more than two captures, because m.groups.year survives a reordering that would break m[3].

Lookahead and lookbehind assert without consuming

\d+(?= kg) matches the digits in "70 kg" but not the " kg" itself, so the match is just 70. That is the point: you can require context without including it in the result.

Lookbehind — (?<=Rs\.)\d+ — works in current browsers and Node, and in Safari from version 16.4. If you need to support older Safari, a capture group is the portable alternative.

Negative forms are often the clearest way to express "not followed by": foo(?!bar) matches "foo" in "foobaz" and not in "foobar".

A pattern is not a parser

Regular expressions cannot count nesting depth, which means they genuinely cannot parse HTML, JSON or arbitrary nested brackets. A pattern can extract from a known, fixed shape, and that is a perfectly good use. A pattern that tries to handle every valid case of a nested format will be long, slow and still wrong on an input you have not thought of yet.

The practical line: if the format can nest, use a parser. If you are pulling a date out of a log line whose shape you control, a pattern is the right tool.

Testing well

Three habits catch most mistakes before they ship:

  • Test the near-miss, not just the hit. A pattern that matches what you want is half the job; a pattern that also matches something you did not want is the bug you will find in production.
  • Paste real data. Hand-typed samples are too clean — no trailing spaces, no stray tabs, no line breaks in awkward places.
  • Check the flags before the pattern. When a pattern behaves oddly, the flags are wrong more often than the pattern is.
