💻 Why Your HTML and CSS Look Wrong — and How to Fix It

October 2026 · 9 min read

A live HTML editor — type markup on one side, see the result on the other — is one of the fastest ways to learn front-end development and one of the fastest ways to test an idea. The immediate feedback removes the save-and-refresh cycle, which matters more for learning than it sounds, because the connection between a change and its effect stays obvious.

This guide covers what to use one for, the mistakes that make the preview behave unexpectedly, and the limits worth knowing before you rely on it.

What a live preview is genuinely good for

  • Learning how a property behaves. Reading that flex-grow distributes free space is one thing; changing the value and watching the boxes move is another.
  • Reproducing a bug in isolation. Stripping a broken layout down to twenty lines usually reveals the cause, and a live editor is the quickest place to do the stripping.
  • Testing an email template. Email clients need table layouts and inline styles, which nobody writes from memory.
  • Checking a snippet before pasting it in. Code from an answer online may be for a different framework version entirely.
  • Teaching. Showing the effect of one changed line is far more effective than describing it.

The mistakes that make a preview misbehave

Styles leaking, or not applying at all

A preview usually renders inside an iframe, which is its own document. A stylesheet in the parent page does not apply inside it, and vice versa. If your CSS seems to be ignored, check that it is inside the preview's own <style> block rather than relying on the page around it.

The same isolation is why a preview will not inherit your site's font or reset. Blank-slate rendering is correct behaviour, and a layout that looks right in the editor can look different on a page that has a CSS reset.

Unclosed tags fail silently

HTML has no syntax errors in the way a programming language does. A missing </div> does not produce an error message — the browser guesses where it should have gone, and the guess is often somewhere you did not expect. The symptom is a layout where everything after a certain point is nested one level too deep.

If a layout breaks after a particular element, count your closing tags from that element backwards. The browser recovering from your mistake is what makes this hard to see.

Self-closing tags that are not

<div /> is not a self-closing div. In HTML, only void elements — img, br, input, hr, meta, link — have no closing tag, and the trailing slash on those is optional. Writing <div /> opens a div that is never closed, which is the previous problem with a different cause.

This catches people coming from JSX, where self-closing any element is required.

Scripts and the preview boundary

Script inside a preview runs in the iframe, not in your page. That is the point — it cannot interfere with the editor. But it also means document.getElementById inside the preview will not find elements in the editor around it, and a console error from the preview appears attributed to the frame.

Many previews also sandbox the frame, which blocks some APIs deliberately. If something works on your own page and not in a preview, sandboxing is a likely cause.

CSS specificity, which explains most "why is this ignored"

When two rules target the same element, the more specific one wins — not the later one. The hierarchy, from weakest:

So #main p { color: blue } beats .highlight { color: red } even if the class rule comes later in the file. Only when specificity is equal does source order decide.

!important wins everything, which is why it should be a last resort — once one rule uses it, overriding that rule requires another, and the cascade stops being predictable.

Box model: the other half of layout confusion

By default, width sets the content box, and padding and border are added outside it. So an element with width: 200px; padding: 20px occupies 240 pixels.

Setting box-sizing: border-box makes width include padding and border, which is what almost everyone expects. Most modern stylesheets apply it globally for exactly that reason:

*, *::before, *::after { box-sizing: border-box }

If your boxes are consistently wider than you set them, this is why.

What a browser editor cannot do

Worth knowing so you do not waste time:

  • No server. Anything needing a backend, a database or a server-side language will not run.
  • Cross-origin requests are blocked unless the other server explicitly allows them, so fetching from most APIs will fail with a CORS error that is not your bug.
  • No build step. JSX, TypeScript, SCSS and bundler imports need compilation first.
  • Not a cross-browser test. You are seeing your own browser's rendering. Something that works in Chrome may differ in Safari.

Where your code goes

Many online editors save your work to their servers so you can share a link. Convenient, and worth a moment's thought if the snippet contains an API key, a client's markup, or anything from a private codebase.

A browser-only editor keeps the code on your device. You lose the shareable link; you keep the certainty that nothing was transmitted.
